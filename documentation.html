Yellow Paper - Spécification Core L1 (Build 2.4.0)

Architecture Institutionnelle & Livre Blanc Technique

Ce document constitue la référence exhaustive absolue de l'infrastructure logicielle, cryptographique et matérielle du protocole Nexus Core Layer-1. Développé en ingénierie souveraine au Burkina Faso par Atlas & Duc Corporation, ce réseau résout le trilemme de la blockchain (Sécurité, Scalabilité, Décentralisation) par une approche de consortium autorité (nBFT), un ancrage monétaire strict et une machine virtuelle sand-boxée à frais constants.

1. Tokénomique & Ingénierie Monétaire

Le réseau L1 Nexus rejette catégoriquement le paradigme spéculatif des blockchains publiques (type ERC-20 flottants). L'infrastructure est conçue comme un outil de souveraineté économique, agissant comme un grand livre de compte immuable (Ledger) pour l'économie réelle de la zone UEMOA et au-delà.

1.1 Paramètres Invariants du Réseau

Les métriques fondamentales suivantes sont encodées en dur dans le binaire du nœud et validées dans le bloc 0 (Genesis). Aucune modification de ces paramètres n'est possible sans un hard-fork approuvé par 100% du consortium.

Total Supply Cap 100,000,000,000 ₳ Offre maximale pré-minée dans la trésorerie au bloc 0. L'inflation algorithmique est mathématiquement fixée à 0.00%.

1.2 Trésorerie On-Chain & Preuve de Réserve (PoR)

Le contrat de trésorerie primaire (Genesis Address: ADC6MH4qsxED6cLtH3NLng5QL6Kvb9HRa8ui) concentre l'intégralité du non-circulant. Le mécanisme de distribution obéit au modèle Mint-and-Burn conditionnel, redéfini ici comme un modèle Release-and-Lock :

  • Cash-in (Dépôt) : Lorsqu'un utilisateur dépose des fonds fiduciaires via Mobile Money ou virement bancaire sur les agrégateurs partenaires, le système API propriétaire déclenche une transaction L1 déplaçant les ₳ correspondants du Vault vers l'adresse Base58 de l'utilisateur.
  • Cash-out (Retrait) : Lors d'une conversion fiat sortante, les AG-COIN ne sont pas détruits ("Burn"). Ils sont transférés en retour vers l'adresse du Vault, garantissant que TotalSupply = CirculatingSupply + VaultBalance soit toujours une constante absolue.
  • Velocity Limits : Pour des raisons de conformité AML/CFT, le backend RPC limite les transferts L1 non-institutionnels à un quantum maximum par bloc, évitant les drainages soudains de liquidité.
Surveillance en Temps Réel
La solvabilité du système peut être auditée à la milliseconde près en exécutant la méthode JSON-RPC nexus_getBalance sur l'adresse publique du Vault, et en la comparant aux réserves fiduciaires certifiées publiées trimestriellement par Atlas & Duc Corp.

2. Architecture du Registre & Topologie nBFT

Contrairement aux blockchains classiques stockant les données sur disque lent (LevelDB), Nexus Core maintient l'intégralité du State Machine (Moteur d'État) en RAM vive pour des temps de réponse sub-millisecondes, combiné à un système de persistance asynchrone (WAL - Write-Ahead Logging) via ledger_mainnet.json.

2.1 Anatomie Stricte d'un Bloc (Block Time: 2000ms)

La cadence est fixée à 2000 millisecondes (2 secondes). Si la Mempool (limitée par sécurité à 50,000 transactions) est vide, le validateur génère un bloc vide de battement de cœur (Heartbeat) pour prouver sa vivacité.

Interface Sérialisée (Format JSON Stocké) TypeScript / JSON
interface NexusBlock { index: number; // Hauteur exacte de la chaîne (ex: 15420) hash: string; // Base58(SHA-256(index + prevHash + timestamp + merkleRoot + validator)) previousHash: string; // Lien indéfectible au bloc n-1 (Base58) timestamp: number; // Horodatage UNIX epoch en secondes validator: string; // Adresse de l'Autorité (Atlas & Duc) ayant forgé merkleRoot: string; // Racine de l'arbre binaire des transactions transactions: Tx[]; // Array d'objets Transaction formatés }

2.2 Arbre de Merkle & Hachage Cryptographique

La propriété merkleRoot est vitale pour les clients légers (Portefeuilles Mobiles) afin de vérifier si une transaction est incluse dans un bloc sans télécharger les centaines de Gigaoctets de la blockchain. Le réseau Nexus utilise un Double SHA-256 récursif encodé en Base58 :

  1. Chaque objet de transaction est stringifié (JSON.stringify) puis haché une première fois.
  2. Les hashs sont appariés deux par deux. Si le nombre de feuilles est impair, le dernier hash est dupliqué contre lui-même (Ex: Hash(C + C)).
  3. Le processus est répété (hachage des concaténations) jusqu'à l'obtention d'un hash racine unique.

2.3 Algorithme de Consensus nBFT (Nexus Byzantine Fault Tolerance)

Le réseau écarte le Proof-of-Work (lent et énergivore) et le Proof-of-Stake (oligarchique). Il utilise le Proof-of-Authority (PoA) avec l'algorithme interne nBFT :

  • Liste Blanche (Allowlist) : Seuls les nœuds dont les adresses figurent dans l'array genesisConfig.validators sont autorisés à signer des blocs.
  • Finalité Absolue : Dès qu'un bloc passe la fonction isValidNewBlock() et est inséré en mémoire locale, il est final. Il n'y a pas de réorganisation de chaîne (Re-orgs), garantissant aux exchanges une certitude instantanée des dépôts.
  • P2P Broadcasting : Les validateurs communiquent via un bus WebSocket dédié (Port TCP/6001). Les messages émis sont strictement typés : NEW_BLOCK et NEW_TRANSACTION.

3. Standard Cryptographique & Résilience Vectorielle

L'infrastructure cryptographique du portefeuille Nexus Core a été conçue en anticipant les évolutions du brute-forcing par ASIC et l'ingénierie sociale. L'encodage hexadécimal complexe est remplacé par une représentation humainement lisible.

3.1 Nomenclature Base58 (Sans Ambiguïté)

Contrairement aux adresses Ethereum (0x...) qui utilisent de l'hexadécimal (incluant O/0 et I/l, sources majeures d'erreurs d'envoi), Nexus Core utilise l'alphabet Base58 exclusif, dépourvu des caractères prêtant à confusion.

123456789ABCDEFGHJKLMNPQRSTUVWXYZabcdefghijkmnopqrstuvwxyz

Chaque identifiant (Adresse de Wallet, Hash de Transaction, Contrat NCRC-20) passe par cet encodage. Les adresses de trésorerie commencent par un préfixe spécifique (ex: ADC... pour Atlas Duc Corporation), et les contrats sont préfixés par ADCC... lors de leur instanciation par la VM.

3.2 KDF (Key Derivation) : La forteresse Argon2id

Pour la sécurisation des mots de passe clients (génération de la Master Key côté front-end ou wallet décentralisé), le protocole impose Argon2id (standard IETF RFC 9106), offrant une résistance hybride infranchissable contre les fermes GPU et les attaques par canaux auxiliaires (Side-channel attacks).

Paramètre Argon2id Valeur Système Justification Sécuritaire (Anti-ASIC)
Memory Cost (m) 65536 (64 MiB) Sature volontairement la mémoire cache L1/L2 des ASICs, rendant la parallélisation matérielle impossible ou hors de prix.
Iterations (t) 4 passes Multiplie le coût CPU de manière linéaire, configuré pour nécessiter ~500ms sur un smartphone moderne.
Parallelism (p) 4 threads Force l'attaquant à bloquer 4 cœurs physiques/logiques par tentative de mot de passe.

3.3 Signature secp256k1 & Vérification L1

Avant d'intégrer la Mempool, le nœud RPC extrait la signature cryptographique du JSON soumis via nexus_sendRawTransaction. L'adresse publique (tx.from) est dérivée de la clé publique contenue dans la signature ECDSA (courbe y² = x³ + 7) et croisée avec le paramètre tx.from pour prévenir le spoofing.

4. Nexus Virtual Machine (NVM) & NCRC-20

Le Layer-1 n'est pas qu'un registre de paiement. Il intègre un moteur d'exécution de code Turing-complet, la NVM (Nexus Virtual Machine). Basée sur l'engine V8 de Node.js via le module natif vm, la NVM permet d'exécuter des Smart Contracts écrits en JavaScript natif, réduisant radicalement la barrière à l'entrée par rapport à Solidity ou Rust.

4.1 Le Modèle "Zero-Deviation Gas"

L'imprévisibilité des frais (Gas Spikes) détruit l'utilisabilité B2B. Nexus Core introduit le Zero-Deviation Gas :

  • Transfert Simple P2P : Coûte un forfait immuable défini par tx.feeMicro (généralement 1000 microA, soit 0.001 ₳).
  • Halt by Timeout : Au lieu d'un système complexe de compteurs de gas par OpCode, la NVM sandboxe le contrat avec un timeout: 50 (50 millisecondes CPU max). Tout contrat impliquant une boucle infinie ou un calcul trop lourd est tué par le Thread V8. La transaction est marquée failed, mais les frais sont conservés par le réseau.
  • Isolation d'État (Deep Copy) : Le contrat ne peut pas modifier l'état global directement. L'objet state lui est passé en copie isolée. Si l'exécution réussit sans crasher, le moteur NexusLedgerState valide le nouvel état et écrase l'ancien dans la Map ledger.contractsState.

4.2 Déploiement & Syntaxe d'un Contrat L1

Un contrat est déployé en soumettant une transaction de type deploy_contract contenant le code source sous forme de chaîne de caractères dans le paramètre code. Voici la structure d'un contrat de base de données d'identité (KYC-Registry) :

Contrat L1 (JS NVM-Compatible)
// Ce code est converti en String et envoyé dans tx.code function execute(state, action, caller) { // 1. Initialisation de l'état si vide if (!state.registry) state.registry = {}; if (!state.owner) state.owner = caller; // 2. Routage de l'action if (action.type === 'init') { return state; } if (action.type === 'register_identity') { if (caller !== state.owner) throw new Error("Non autorisé (Admin only)"); const userAddress = action.params.user; const kycdHash = action.params.hash; state.registry[userAddress] = { kycStatus: 'verified', documentHash: kycdHash, timestamp: Date.now() }; return state; } throw new Error("Action Inconnue"); }
Sécurité NVM
Le contexte `vm.createContext()` de Node.js est purgé des modules systèmes (pas de `fs`, `http`, ou `require()`). Le code n'a accès qu'à l'objet `state`, `action`, `caller`, et aux fonctions mathématiques natives basiques.

5. Opérations B2B & Spécifications Matérielles

5.1 Cluster de Validation Atlas & Duc (Hardware Tier 1)

Le réseau principal étant un Ledger "In-Memory" pur avec persistance synchrone haute fréquence, les spécifications des serveurs bare-metal hébergés par le consortium répondent à des normes industrielles draconiennes :

Couche d'Ingénierie Configuration Strict Requise Raison Opérationnelle
Compute (CPU) Dual AMD EPYC (64 Cores / 128 Threads) Validation multi-threadée de l'intégrité de la Mempool (ECDSA + Double Merkle) à grande échelle.
State RAM 256 GB RAM DDR5 ECC L'objet `this.balances` (des dizaines de millions de comptes projetés) est maintenu en permanence dans la V8 Heap Memory.
I/O (Stockage) Grappe NVMe PCIe 5.0 (RAID 10) Le dump de l'état via `fs.writeFileSync(TEMP_DB_FILE)` toutes les 2 secondes nécessite des débits I/O de classe datacenter (> 10 GB/s).
Réseau (Bande Passante) Lien dédié 10 Gbps symétrique Diffusion instantanée du P2P WebSocket (`port: 6001`) pour garantir le consensus en < 50ms sur le territoire.

5.2 Continuité d'Activité & Plan de Reprise (PRA/PCA)

Le moteur logiciel L1 est conçu pour résister aux pannes électriques abruptes (courantes dans certains datacenters). La fonction saveState() utilise un patron d'écriture atomique : l'état est d'abord sérialisé dans un fichier temporaire ledger_mainnet.tmp.json. Uniquement si l'écriture est terminée sans erreur, une instruction système fs.renameSync() (qui est atomique au niveau de l'OS) remplace le fichier de base de données principal. En cas de coupure (SIGINT/SIGTERM/Crash), la corruption de données est mathématiquement impossible.

5.3 Intégration Institutionnelle & Cadre Légal UEMOA

En tant qu'infrastructure "Compliance-by-Design", Nexus Core fournit aux institutions (Banques, SFD, Opérateurs Telco) une suite d'APIs permettant :

  • La génération de portefeuilles sous séquestre (Multisig ou contrôlés par Smart Contract).
  • L'inscription irréfutable des empreintes d'audit (Audit Trails) de conformité AML/CFT directement dans la blockchain.
  • La supervision en temps réel des flux de trésorerie via les endpoints d'exploration on-chain.
