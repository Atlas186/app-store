Documentation Core L1 - Build 2.4.0 (Octobre 2026)

Livre Blanc Technique & Architecture Institutionnelle

Ce document constitue la référence exhaustive de l'infrastructure logicielle et matérielle du protocole Nexus Core L1. Il détaille la politique monétaire adossée, les mécanismes du consensus nBFT, la machine virtuelle (NVM), les normes cryptographiques (Argon2id/ECDSA) et la topologie du réseau P2P ingénierés par Atlas & Duc Corporation au Burkina Faso.

1. Tokénomique & Souveraineté Économique

L'écosystème Nexus Core L1 opère en rupture totale avec les paradigmes spéculatifs des blockchains publiques (volatilité, congestion). Il s'agit d'une infrastructure souveraine, décentralisée par consortium, et à parité fiduciaire stricte, développée pour numériser l'économie réelle africaine (agriculture, logistique, santé).

1.1 Paramètres Fondamentaux du Réseau L1

Paramètre L1 Valeur Système Description Spécifique

Total Supply 100,000,000,000 ₳ Offre maximale cryptographiquement gravée dans le bloc 0 (Genesis). L'inflation réseau est strictement de 0%.

1.2 Économie en Boucle Fermée & Trésorerie On-Chain

Pour immuniser l'infrastructure contre les attaques de marché, Nexus Core implémente un modèle "Closed-Loop" géré par le smart contract de trésorerie (AGI9e3jK4Ly5xMv8PqRw2TbFnVdC1Xg6hYuZ7AsBmN1x) :

  • Isolation d'Exchange : Le token n'est audité et négocié que via les infrastructures DEX propriétaires et les agrégateurs B2B d'Atlas & Duc (ex: via l'API REST CoinMarketCap interne).
  • Mécanisme No-Burn : Lors de conversions fiat sortantes (Cash-out via Mobile Money), les jetons ne sont pas détruits ("Burned"). Ils sont restitués à la réserve du protocole (Vault) pour maintenir l'intégrité de la masse monétaire.
  • Auditabilité Temps Réel : Le RPC nexus_getBalance sur l'adresse de trésorerie permet à tout moment de vérifier la solvabilité du système.

2. Architecture du Registre (Ledger) & Topologie P2P

Le moteur d'état (State Machine) est programmé en Node.js industriel. Il est maintenu en RAM et persisté via un flux I/O asynchrone sécurisé (ledger_mainnet.json & fichier `.tmp` transactionnel) pour éviter toute corruption lors d'arrêts brutaux (SIGINT/SIGTERM).

2.1 Structure du Bloc & Mempool (Block Time: 2000ms)

Le validateur leader forge un bloc de manière déterministe toutes les 2 secondes. La Mempool (file d'attente) limite dynamiquement sa taille à MAX_MEMPOOL_SIZE = 5000 transactions pour prévenir les vecteurs d'attaque DDoS.

Interface L1Block (TypeScript Spec)
interface NexusBlock { index: number; // Hauteur de la chaîne hash: string; // SHA-256(index + prevHash + timestamp + merkleRoot + validator) previousHash: string; // Chaînage cryptographique timestamp: number; // Horodatage UNIX (Secondes) validator: string; // Adresse de l'Autorité ayant forgé le bloc merkleRoot: string; // Racine de l'arbre binaire des transactions stateRoot: string; // Hash de l'état global (Balances & NVM State) transactions: Tx[]; // Tableau d'objets Transaction }

2.2 Arbre de Merkle (Double SHA-256)

La merkleRoot est calculée via une fonction récursive de hachage Double SHA-256. Si le nombre de feuilles (transactions) est impair, le dernier hash est dupliqué. Ce mécanisme permet les preuves SPV (Simplified Payment Verification) pour les clients légers (Mobile).

2.3 Consensus nBFT (Proof of Authority)

Contrairement au Nakamoto Consensus (PoW), le Nexus Byzantine Fault Tolerance (nBFT) offre une finalité absolue et immédiate. Dès qu'un bloc est inséré dans l'array this.blocks, il est irréversible (0 Re-org). Les nœuds communiquent via le port P2P 6001 via WebSocket, gérant le routage via les messages REQUEST_CHAIN, NEW_BLOCK, et NEW_TRANSACTION.

3. Standards Cryptographiques & Résilience ASIC

L'infrastructure cryptographique du portefeuille Nexus Core a été spécifiquement conçue pour contrer l'évolution des calculateurs quantiques préliminaires et des fermes de minage ASIC dédiées au brute-force.

3.1 Key Derivation Function : Argon2id

Les clés privées ne sont jamais stockées brutes. Elles sont dérivées via Argon2id (standard IETF RFC 9106), offrant une résistance hybride (GPU et attaques par canaux auxiliaires).

Paramètre Argon2id Valeur Strict Justification Sécuritaire
Memory Cost (m) 65536 (64 MiB) Sature la mémoire cache des ASIC, rendant le calcul matériel inopérant.
Iterations (t) 4 passes Augmente le coût CPU linéaire sans compromettre l'UX mobile.
Parallelism (p) 4 threads Force l'attaquant à allouer 4 cœurs physiques par tentative.

3.2 Courbe Elliptique secp256k1 & Adressage

Les transactions sont signées via l'algorithme ECDSA sur la courbe y² = x³ + 7. L'adresse L1 publique est dérivée de la clé publique de la manière suivante :

const pubKeyHash = RIPEMD160(SHA256(publicKeyBytes)); const address = "0x" + pubKeyHash.toString('hex'); // Les adresses de contrats générées par la NVM sont préfixées par "AGIC"

4. Nexus Virtual Machine (NVM) & Tokénisation

Le L1 intègre un moteur d'exécution de code Turing-complet, la NVM. Ce moteur est isolé de l'hôte matériel via le module natif vm de Node.js (V8 Sandboxing).

4.1 Modèle de Gaz Zéro-Déviation (Zero-Deviation Gas)

L'inflation des frais (Gas Spikes) rend l'usage commercial d'Ethereum ou Solana impossible pour l'industrie traditionnelle. Nexus Core résout ce problème avec une tarification rigide codée en dur (Hardcoded) :

  • Exécution d'un transfert simple : Coûte exactement 1000 microA (0.001 ₳ = 0.001 FCFA).
  • Exécution NVM (Contrat) : Facturé au gaz utilisé, mais avec un gasPrice fixe.
  • Prévention des Boucles Infinies : Le contexte V8 est créé avec un timeout: 50 (50 millisecondes max). Tout contrat dépassant ce délai est interrompu (Halt), la transaction échoue, mais le gaz est consommé pour rémunérer le validateur.

4.2 Standard NCRC-20 & Stockage d'État

Lors d'une transaction de type deploy_contract, le L1 stocke la logique (Code) dans ledger.contractsCode et instancie l'état (State) dans ledger.contractsState.

NVM Sandboxed Execution (Core Engine)
class NexusLedgerState { executeContract(code, currentState, action, caller) { // 1. Isoler l'état pour empêcher les mutations illégales (Deep Copy) const sandbox = { state: currentState ? JSON.parse(JSON.stringify(currentState)) : {}, action, caller }; const context = vm.createContext(sandbox); try { // 2. Compilation JIT et injection du point d'entrée "execute()" const script = new vm.Script(`${code}\nexecute(state, action, caller);`); // 3. Exécution stricte: Max 50ms, RAM limitée au contexte V8 return script.runInContext(context, { timeout: 50 }); } catch (e) { console.error(`[NVM ERREUR] Échec d'exécution du contrat: ${e.message}`); return null; // Rollback de l'état } } }

5. Opérations Validation & Intégration Client

5.1 Spécifications Matérielles des Nœuds Valideurs

Pour assurer le traitement de la base de données en RAM (this.balances, this.blocks) sur un réseau principal, le consortium impose l'architecture matérielle suivante :

Composant Configuration Minimale Raison Technique
CPU 32 Cores / 64 Threads (x86_64) Traitement parallèle des signatures ECDSA dans la Mempool et calcul Merkle.
Mémoire (RAM) 128 GB DDR5 ECC Le NexusLedgerState conserve l'intégralité du state en mémoire vive pour des I/O sub-millisecondes.
Stockage 4 TB NVMe PCIe 4.0 (RAID 10) Persistance ultra-rapide de ledger_mainnet.tmp.json toutes les 2 secondes.

5.2 API JSON-RPC & Format de Transaction

Le nœud expose le port HTTP 9545 pour le trafic RPC. L'endpoint nexus_sendRawTransaction accepte des payloads JSON stricts. Le nonce (nombre de transactions déjà envoyées par l'adresse) doit être parfaitement synchronisé pour éviter l'erreur -32000 (Transaction désynchronisée).

5.3 Conformité UEMOA & Audit AML

L'infrastructure est "Compliance-Ready". Les wallets B2B créés via les SDK Atlas & Duc intègrent une vérification KYC (Biométrie/CNI) dont l'empreinte de validation (Hash) peut être inscrite dans le champ data des transactions L1. Les smart contracts de micro-finance AGI intègrent nativement des algorithmes de plafonnement (Velocity Limits) pour lutter contre le blanchiment d'argent.
